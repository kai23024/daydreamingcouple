# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install         # install dependencies
npm run dev          # dev server (default http://localhost:3000)
npm run build        # SSR/Node production build
npm run generate     # static site generate -> .output/public (used for Firebase Hosting)
npm run preview      # preview a build locally
```

There is no test suite and no lint script configured. `npx nuxi typecheck` is broken in this repo (the installed `typescript`/`vue-tsc` versions are mismatched — `vue-tsc` requires an older TS export path); don't try to fix that unless asked, rely on `npm run generate` succeeding as the correctness signal instead.

## Architecture

Nuxt 4 app using the `app/` source directory convention (routes, components, etc. live under `app/`, not the project root).

- **Content model**: all article/category content is centralized in `app/data/site.ts` as plain arrays (`categories`, `articles`) with helper functions `articlesByCategory(slug)`, `categoryBySlug(slug)`, `articleById`/lookup by `id` in `article/[id].vue`, and `articleExcerpt(article)` — no stored `excerpt` field (removed 2026-08-15); the card/preview text is always derived by finding the first plain-string element in `body`, so the article's opening paragraph doubles as its preview. `body: (string | ArticleImageBlock | ArticleCaptionBlock | ArticleHeadingBlock)[]` is a mixed array rendered top-to-bottom on the detail page (`article/[id].vue`): plain strings render as `<p>` paragraphs, `{ images: string[] }` blocks render as a photo (one image) or a side-by-side pair (two images) at that exact position, `{ caption: string }` blocks render as small muted gray text with no background (`text-xs text-morandi-400`) — used for camera/lens EXIF lines that source drafts mark as "此行文字請用灰底" — and `{ heading: string, level?: 1|2 }` blocks render bold, level 1 larger than level 2, for section/sub-section titles in verbatim-mode articles. There is no CMS or backend — adding a new article or category means editing this one file.
- **Routing**: `app/pages/index.vue` is the homepage and shows the latest 3 articles (sorted by `date` descending) from 4 categories — taiwan/japan/global/food — each rendered with `CategorySection` (see below). `app/pages/[slug]/index.vue` is a dynamic route that renders any category listing page (taiwan/japan/global/photography/food/stay/trips) by looking up `slug` against `categoryBySlug`. `app/pages/article/[id].vue` is a **flat, top-level** route for individual article pages (`/article/<id>`) — it is intentionally *not* nested under `[slug]/` (e.g. `[slug]/[article].vue`). That nested-dynamic-route shape was tried first and had a real bug in this project: Nitro's static prerenderer served the *category listing* page's HTML at the nested article URLs instead of the article page. Keep article URLs flat under `/article/` unless that's independently verified fixed upstream. `app/pages/about.vue` is the only fully static page.
- **Components**: `AppHeader`/`AppFooter` (global chrome, wired into `app/app.vue`), `ArticleCard` (clickable card linking to `/article/<id>`, used in listings), `CategorySection` (standard grid; the only homepage section layout). The homepage originally used 4 *different* section layout components (one per featured category) as a deliberate anti-repetition design choice — the user explicitly asked (2026-08-15) to reverse that and make every homepage section the same size/layout for visual consistency, so `FeaturedSection`/`ScrollSection`/`BentoSection` were deleted and everything now uses `CategorySection`. Don't reintroduce per-section layout variety on the homepage without being asked again.
- **Images**: two supported modes, chosen per article. (1) **Placeholder mode** (default, no source photos available): hero/card images are generated at render time from `https://picsum.photos/seed/<seed>/...` using the article's `seed` field — this is what every article had originally, and still applies whenever `hero` is unset and `body` has no image blocks. (2) **Real-photo mode** (used when the draft folder came with actual photos, e.g. `kyunghee-univ`, `seoul-forest`): real files live under `public/images/<article-id>/` (served as-is by Nuxt at `/images/<article-id>/<filename>`; keep original filenames when ASCII, rename any CJK filename — e.g. a "XX地圖.jpg" map photo — to a plain ASCII name like `map.jpg` on copy, since untyped CJK URLs are needlessly fragile). Set `Article.hero` to one of those paths to use it as the hero/card image instead of the picsum fallback (`ArticleCard.vue` and `article/[id].vue` both do `article.hero || picsum-seed-url`); place `{ images: [...] }` blocks inline in `body` at the position the source article called for a photo (one path = full-width, two paths = side-by-side pair, matching the `left/right` framing docx drafts often specify). Don't back-fill placeholder-mode articles with real photos speculatively — only do this when an actual draft folder with real photos exists for that article.
- **Styling**: Tailwind via `@nuxtjs/tailwindcss`, using an explicit custom CSS entry at `app/assets/css/tailwind.css` (module option `tailwindcss.cssPath` in `nuxt.config.ts` points at it explicitly — the module's path-guessing default did not pick this up reliably, hence the explicit config). That file also carries small base-layer rules (smooth scroll, `text-wrap: balance` on headings, a visible focus ring). `tailwind.config.ts` at the project root extends `fontFamily` (`sans` → Noto Sans TC, `serif` → Noto Serif TC, loaded via Google Fonts `<link>` tags in `nuxt.config.ts`'s `app.head`) and `colors` with two custom palettes, `morandi` (neutral warm beige/taupe, replaces `stone`) and `clay` (muted terracotta accent, replaces `amber`) — the site was originally dark-themed (stone/amber) but was redesigned 2026-08-15 to this light "Morandi beige" palette at the user's request; don't revert to stone/amber. Traditional Chinese (`zh-Hant`) is the primary content language throughout.
- **UI design**: the visual/layout design was originally audited against the MIT-licensed [taste-skill](https://github.com/Leonxlnx/taste-skill) rules (anti-repetition of layout families, no em-dashes, visible focus states, tactile press states, custom 404 page at `app/error.vue`). The anti-repetition-of-layout-families rule was later deliberately overridden for the homepage specifically (see "Components" above) at explicit user request — the other rules (focus states, tactile press states, custom 404, em-dash avoidance in *rewritten* prose) still apply. If asked to redesign or polish the UI further, re-fetch and re-apply that skill's checklist rather than guessing at generic "modern UI" changes, but don't assume every rule is still in force without checking current state first.
- **Rendering mode**: configured for static generation — `nitro.prerender` in `nuxt.config.ts` explicitly lists top-level routes (plus `crawlLinks: true`, which is what actually discovers per-article and per-category pages by following links). If a new top-level route is added that isn't reachable by crawling from the listed seed routes, add it to that `routes` list or it won't be prerendered.

## Windows/PowerShell gotcha

This repo has Nuxt page filenames containing square brackets (e.g. `[slug]`, `[id]`). In Windows PowerShell, `Remove-Item "app/pages/[slug].vue"` silently does **not** delete that file — PowerShell's wildcard engine parses `[slug]` as a character class and the path just doesn't match anything (no error). This exact bug caused a real production incident (stale route files coexisted with their replacements, corrupting prerendered output). Always use `Remove-Item -LiteralPath ...` (or `Remove-Item -LiteralPath (Get-Item ...)`) for any path containing `[` or `]` in this repo.

## Deployment

Static output (`.output/public` from `npm run generate`) deploys to **Firebase Hosting** (project `daydreamingcouple-1707b`, configured by `firebase.json` and `.firebaserc`). Deployment is automated: `.github/workflows/firebase-hosting-merge.yml` runs `npm ci && npm run generate` and deploys on every push to `main`, authenticating with the `FIREBASE_SERVICE_ACCOUNT_DAYDREAMINGCOUPLE_1707B` repo secret. Manual deploy (`firebase deploy --only hosting`) requires a local `firebase login`, which has been unreliable in this environment — prefer letting CI deploy.
